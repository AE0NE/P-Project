## 1. 이번 주에 내가 맡는 역할

내 역할은 **공식 문서를 모델과 규칙이 읽을 수 있는 입력으로 만들고, 조건을 원문에서 다시 확인할 수 있게 하는 것**입니다. 모델과 비교할 규칙 추출기, 두 추출기에 함께 적용할 후처리, 로컬 실행 절차도 맡습니다.

예를 들어 표에서 `30만 원 / 10% / 5천 원`만 가져오면 각각 실적·비율·한도인지 알기 어렵습니다. 표 제목과 행·열의 설명, 적용되는 각주를 함께 남겨야 합니다. 이 문맥을 잃어버리면 모델을 잘 학습하더라도 빠진 정보를 복구하기 어렵습니다.

| 내가 책임질 일 | 다른 담당자와 나눌 일 |
| --- | --- |
| 자료 접근성·문서 구조 확인, 원본·출처 기록 | 손영원: 최종 상품 선정, 파일럿 배정·데이터 분할, 이용조건 검토 |
| 본문·표·각주를 포함한 조건 블록과 원문 대응 | 손영원: 주석 기준, 박세렴: 화면의 근거 표시 |
| 문맥을 활용하는 규칙 추출기 | 손영원: 라벨 경계·정답·공정한 성능 비교 |
| 금액·단위 정리와 명확한 관계 연결 | 박서연: 공통 결과 형식과 DB 저장 |
| CPU 실행·설치 안내와 환경 재현 | 손영원: 모델 측정 기준, 박서연: 서버·DB 실행 |

기존 Python·JSON·Linux·실행 자동화 경험을 입력 처리와 재현 절차에 활용합니다. 이번 과제의 AI는 한국어 조건 추출 모델이므로, 로컬 생성형 LLM 서버나 Agent를 새로 구축하는 일을 첫 주 목표에 추가하지 않습니다.

## 2. 이번 주 목표와 우선순위

> **학습용 파일럿 문서 한 건에서 문맥과 출처를 보존한 조건 블록을 만들고, 규칙 결과·공통 후처리 결과를 같은 형식으로 서버와 화면에 전달합니다.**

모든 문서 형식을 한 번에 처리하기보다 파일럿에서 실제로 검증할 수 있는 입력부터 지원합니다. 우선 5~10개 블록을 원문과 대조해 손영원에게 전달하고, 공동 주석이 실제 블록 10개 이상으로 이어질 수 있도록 보완합니다. 블록 수를 맞추려고 같은 문장을 복제하거나 의미 없이 잘게 나누지 않습니다.

## 3. 오늘 바로 시작할 일

### DP-W1-01 사용할 수 있는 자료와 첫 입력을 정합니다

먼저 README를 읽고 손영원과 파일럿 후보를 확인합니다. 분석 범위는 일반 신용카드의 온·오프라인 정률 할인·포인트 적립이며, 플랫폼 제휴카드는 제외합니다. 최종 상품 선정과 학습 7·검증 2·시험 3 상품군 분할은 PM과 함께 정합니다.

오늘의 첫 작업은 다음 순서입니다.

1. 후보 상품의 공식 상품 페이지·상품설명서 위치를 확인합니다.
2. 자료를 실제로 확보할 수 있는지, HTML·텍스트 PDF·이미지 위주 문서 중 무엇인지 구분합니다.
3. 이용조건 확인 상태를 기록하고, 사용 가능한 자료에서 PM이 지정한 학습용 파일럿을 정합니다.
4. 파일럿의 본문·표·공통 유의사항에서 어떤 문맥을 함께 가져와야 할지 표시합니다.
5. 첫 지원 입력과 다른 팀원에게 전달할 날짜를 합의합니다.

처음부터 HTML과 PDF를 모두 완벽하게 지원할 필요는 없습니다. 확보한 파일럿을 보고 한 입력 경로를 먼저 선택하고, 다른 형식은 지원 여부와 남은 작업을 기록합니다. 읽기 쉬운 공식 HTML을 먼저 쓰더라도 PDF까지 처리했다고 보고하지 않습니다.

| 출처 목록에 남길 항목 | 기록할 내용 |
| --- | --- |
| 상품·문서 식별 | 상품군 ID, 문서 ID, 상품명, 문서 종류·버전 |
| 출처와 시점 | 공식 URL, 확보일, 확인 가능한 적용 시점 |
| 확보 상태 | 후보·접근 확인·파일 확보·처리 가능 여부를 구분 |
| 이용조건 | 열람·확보·학습·자동수집·재배포의 확인 상태와 근거 |
| 원본 대조 | 확보 파일의 해시, 로컬 보관 위치 |
| 개발 용도 | 학습용 파일럿 여부, PM과 확인한 분할 |

공개 열람 가능성을 학습·자동수집·재배포 허가와 같은 뜻으로 기록하지 않습니다. 첫 주에는 필요한 자료를 소규모로 확인하고, 자동수집은 정책·이용조건을 확인한 범위에서만 검토합니다. 확인되지 않은 이용조건을 임의로 확정하지 않습니다.

같은 상품의 HTML·PDF·개정본은 같은 상품군으로 관리합니다. 반복 개발한 파일럿을 나중에 최종 시험군으로 옮기지 않고, 시험 자료를 보며 파서·규칙을 개선하지 않습니다. 원본 문서·가공 자료는 저장소의 데이터 관리 원칙에 따라 보관합니다.

## 4. 문서를 읽고 검증할 수 있는 블록으로 만듭니다

### DP-W1-02 문맥이 유지되는 입력을 만듭니다

첫 주 문서 처리 흐름은 다음과 같습니다.

```text
공식 자료와 출처 확인 → 원본 보존·식별
                           ↓
본문·표·각주 읽기 → 문맥 블록과 출처 대응 구성
                           ↓
원문 대조 → 보존 텍스트·블록 버전 확정
                           ↓
같은 블록을 규칙·모델·주석·검토 화면에서 사용
```

블록은 문장을 일정 길이로 자른 조각이 아니라 **조건을 해석하는 데 필요한 문맥을 묶은 단위**입니다. 표의 한 행을 가져올 때 제목·열 이름·적용되는 각주도 확인합니다. 공통 각주는 적용 대상을 확인하지 않은 채 모든 혜택에 붙이지 않습니다.

| 자료 구조 | 먼저 확인할 부분 | 첫 주 처리 원칙 |
| --- | --- | --- |
| 본문 | 혜택 제목과 조건 문장의 연결 | 제목·문단 순서와 출처를 보존 |
| 표 | 행·열 헤더, 병합 셀, 단위 | 값만 뽑지 않고 헤더와 대응 관계를 남김 |
| 각주·유의사항 | 본문 표시와 적용 범위 | 참조 관계가 명확하면 연결, 애매하면 보류 |
| 여러 단·페이지 | 읽는 순서, 이어지는 표·문장 | 잘못 합쳐졌는지 원문과 대조 |
| 이미지·추출 실패 | 텍스트 유무와 깨진 내용 | 빈 결과를 정상 완료로 취급하지 않음 |

**기술 선택은 실제 자료를 보고 확정합니다.** 다음은 첫 시도 후보입니다.

| 기술 | 사용 목적 | 선택 이유·한계 |
| --- | --- | --- |
| Python · JSON · pathlib · hashlib | 파일 처리, 구조화 결과·해시 기록 | 기존 자동화 경험을 활용하고 처리 과정을 재현하기 위해 |
| Beautiful Soup | 확보한 HTML의 본문·표 구조 읽기 | HTML 트리를 탐색하는 데 사용. 자바스크립트 실행이 필요한 페이지의 내용까지 자동 확보한다고 가정하지 않음. [공식 문서](https://www.crummy.com/software/BeautifulSoup/bs4/doc/) |
| pdfplumber | 텍스트 PDF의 본문·표·위치 확인 | 문자·표·위치 정보를 살펴볼 수 있는 초기 후보. 텍스트 PDF에 적합하며 OCR을 제공하지 않음. [공식 저장소](https://github.com/jsvine/pdfplumber) |
| Python re | 문맥 키워드·패턴에 따른 조건 구간 탐색 | 규칙의 근거와 예측 범위를 확인하기 위해. [공식 문서](https://docs.python.org/3/library/re.html) |

PDF에서 글자가 추출된다고 표의 의미까지 정확히 복구되는 것은 아닙니다. 표 헤더·각주가 빠지거나 읽는 순서가 달라질 수 있으므로 사람이 대조합니다. 이미지 문서나 복잡한 병합 표는 첫 주 지원 범위에서 보류할 수 있으며, 실제 보류 수와 이유를 남깁니다.

### 원본·보존 블록·모델 입력을 구분합니다

- 원본 파일은 바꾸지 않고 출처·버전·해시로 식별합니다.
- 문서에서 읽어 구성한 블록 텍스트는 주석·화면·추출이 참조할 기준 문자열로 보존합니다.
- PDF에서 구성한 텍스트는 원본 파일의 바이트 구간과 같은 정보가 아닙니다. 페이지·셀·추출 단어 등 확인 가능한 출처 대응을 별도로 남깁니다.
- 블록에 제목·헤더를 붙였다면 각 부분의 출처를 구분합니다. 모델 입력을 추가로 조립하면 보존 블록으로 돌아가는 대응을 남깁니다.
- 공백·줄바꿈·한글 정규화를 바꾸면 문자 위치도 다시 확인합니다. 주석한 뒤 텍스트만 바꾸고 기존 정답 위치를 그대로 사용하지 않습니다.
- 정확한 PDF 좌표가 없으면 만들어 넣지 않습니다. 블록·페이지·출처 확인과 PDF 위의 정밀 강조는 다른 완료 항목입니다.

입력 256토큰은 초기 모델 기준입니다. 손영원과 합의한 토크나이저로 제목·헤더·특수 토큰을 포함한 길이를 확인합니다. 글자 수만으로 토큰 수를 보장하거나 긴 블록의 뒷부분을 조용히 잘라내지 않습니다. 너무 길면 필요한 문맥이 유지되도록 나누고 규칙·모델에 같은 입력을 제공합니다.

**첫 전달 목표:** 원문 대조한 실제 블록 5~10개와 출처·위치 정보를 11/3 전후에 손영원에게 전달합니다. 공동 주석이 10개 이상으로 이어지도록 보완하되, 초기 이중 주석 30~50개·전체 250~400개 목표를 첫 주 실적으로 기록하지 않습니다. 주석 지침과 최종 정답 조정은 손영원이 담당하며, 배정받은 독립 주석은 공동 수행합니다.

## 5. 팀이 같은 입력·출력을 쓰도록 연결합니다

### DP-W1-03 공통 형식과 위치 기준을 확인합니다

공통 형식 초안은 박서연이 작성합니다. 박신혁은 파싱·규칙 출력이 그 형식으로 만들어지는지 확인하고, 손영원은 주석·모델·평가에 쓸 수 있는지, 박세렴은 원문을 표시할 수 있는지 확인합니다.

| 단계 | 전달할 정보 | 확인할 담당자 |
| --- | --- | --- |
| 문서 확보 | 상품군·문서 ID, URL·시점·버전·해시, 합성·실제 구분 | 손영원·박서연 |
| 파싱 | 블록 ID, 보존 텍스트, 제목·표 문맥, 출처 대응 | 손영원·박서연·박세렴 |
| 규칙 추출 | 조건 유형, 시작·끝 위치, 원문 값, 규칙 버전 | 손영원·박서연 |
| 공통 후처리 | 정리한 값·단위·연산자, 명시적 관계·근거, 검토 필요 사유 | 손영원·박서연·박세렴 |
| 실행 | 입력·처리 버전, 실제 실행 방식, 성공·실패·보류 | 박서연 |

아래는 다른 팀원 계획과 맞추기 위한 **합성 블록의 추출 결과 예시**입니다. 파싱 단계는 블록과 출처를 만들고, `spans`는 추출 단계에서 추가합니다. 실제 전달에는 문서 ID·버전·출처 정보도 필요합니다.

```json
{
  "block_id": "SYN-B001",
  "offset_unit": "unicode_code_point",
  "text": "편의점 10% 할인",
  "spans": [
    {"type": "TARGET", "start": 0, "end": 3, "text": "편의점"},
    {"type": "RATE", "start": 4, "end": 7, "text": "10%"}
  ]
}
```

0부터 시작하고 끝은 포함하지 않는 예시입니다. 문자 단위는 합의 전 제안이며, Python·브라우저에서 같은 구간을 가리키는지 확인합니다. 이모지가 포함된 합성 문장도 점검합니다. 위치가 맞지 않으면 정상 근거처럼 반환하지 않고 오류·보류 사유를 남깁니다.

**완료 기준:** 같은 샘플을 서버가 읽고 화면이 표시할 수 있으며, 원문 값과 범위가 일치합니다. 자동 확인한 문자열 일치와 실제 문서에서의 의미·문맥 확인은 구분해 기록합니다. 필드·단위를 혼자 바꾸지 않고 변경 이유와 영향을 공유합니다.

## 6. 규칙 기반 추출기를 만듭니다

### DP-W1-04 숫자와 주변 문맥을 함께 확인합니다

규칙 추출기는 모델이 준비되기 전 연결에 사용하고, 최종적으로는 모델과 비교할 Baseline이 됩니다. 첫 버전은 작게 시작하되, 최종 비교에서 일부러 약한 규칙을 사용하지 않도록 처리 범위·오류를 계속 기록합니다.

| 유형 | 규칙을 설계할 출발점 | 혼동을 확인할 부분 |
| --- | --- | --- |
| TARGET | 혜택 제목·업종·가맹점 문구 | 제외 대상의 이름을 실제 혜택 대상으로 잘못 추출하는지 |
| RATE | 할인·적립 문맥의 퍼센트 | 연체이자율 등 혜택과 관계없는 비율을 포함하는지 |
| SPEND | 전월·이용실적 문구와 금액·비교 기준 | 혜택 한도 금액과 혼동하는지 |
| LIMIT | 월·건별·합산 등 한도 문맥과 금액 | 전월 사용금액을 할인한도로 잘못 읽는지 |
| SPEND_EXCL | 실적 산정 제외 문구와 대상 | 혜택 제외와 구분되는지 |
| BENEFIT_EXCL | 할인·적립 미적용 문구와 대상 | 실적 제외와 구분되는지 |

위 표는 규칙 설계 방향이며 확정된 주석 경계를 뜻하지 않습니다. `30만 원`만 선택할지 `30만 원 이상`까지 포함할지, 제외 목록의 범위와 중첩 우선순위는 손영원의 주석 지침에 맞춥니다. 모델의 단일 BIO 표현과 비교할 수 있는 기준을 사용합니다.

규칙 출력에는 최소한 블록 ID·유형·시작·끝 위치·원문 값이 있어야 합니다. 어떤 규칙이 만든 결과인지도 추적할 수 있게 합니다. 같은 문구가 여러 번 나오면 첫 검색 위치를 재사용하지 않고 실제 매칭된 각 위치를 기록합니다. Python 정규식의 매칭 구간을 이용하는 방식부터 확인합니다. [Python re 안내](https://docs.python.org/3/library/re.html)

첫 구현 순서는 다음과 같습니다.

1. 학습용 블록과 주석 지침에서 실제 표현을 확인합니다.
2. 유형별 패턴과 필요한 제목·헤더 문맥을 적습니다.
3. 합성 예시로 구간·유형 출력이 맞는지 확인합니다.
4. 실제 학습용 블록에서 원문·정답과 대조합니다.
5. 누락·오탐·경계 오류를 나눠 규칙 버전과 함께 남깁니다.

파일럿에 없는 유형은 확인되지 않았다고 기록합니다. 합성 문장에서 동작한 유형과 실제 자료에서 검증한 유형을 구분합니다. 조건을 찾지 못했다고 없음으로 확정하거나, 모든 숫자에 임의의 라벨을 붙이지 않습니다.

**완료 기준:** 공통 형식으로 규칙 결과가 실행되고, 작성한 유형·실제 확인한 유형·부족한 사례를 보고할 수 있습니다. 첫 주에 높은 F1을 달성했다고 가정하지 않습니다.

## 7. 규칙과 모델이 함께 사용할 후처리를 만듭니다

### DP-W1-05 추출과 후처리를 분리합니다

다음 두 작업을 코드와 결과에서 구분합니다.

```text
같은 조건 블록 → 규칙 추출기 → 원문 조건 구간
               모델 추출기 → 원문 조건 구간
                              ↓
                 같은 공통 후처리
                              ↓
          정리한 값·단위·명시적 관계·검토 필요 사유
```

조건 구간을 찾는 규칙과, 이미 찾은 구간의 값을 정리하는 규칙을 한곳에 섞지 않습니다. 모델 출력도 같은 후처리를 사용할 수 있어야 합니다. 평가할 원래 구간·유형은 별도로 보존합니다.

**값 정리의 첫 범위**

- `30만 원 이상`은 금액·단위·비교 기준으로 나누되 원문을 그대로 남깁니다.
- `5천 원`은 `5000원`처럼 표현을 정리하고 월·건별 기간을 보존합니다.
- 비율은 값과 단위의 저장 기준을 박서연과 맞춥니다. `10%`를 `10`과 `%`로 저장하는지 다른 방식인지 명시합니다.
- 원·포인트·퍼센트는 다른 단위로 관리하며, 포인트를 원화로 임의 환산하지 않습니다.
- 미확인·명시적 없음·숫자 0을 구분하고, 해석하지 못한 표현은 원문과 사유를 남깁니다.

**관계 연결은 명확한 근거가 있을 때 진행합니다.** 다음은 직접 만든 설명용 사례입니다.

| 문구 | 연결할 내용 |
| --- | --- |
| 편의점과 카페 할인은 합산하여 월 5천 원 한도 | 두 혜택이 같은 한도를 참조하고 합산 근거를 보존 |
| 편의점 월 5천 원, 카페 월 5천 원 | 같은 금액이라는 이유로 공유 한도로 합치지 않음 |
| 통합 할인한도 적용, 참조 표는 확인되지 않음 | 한도·대상 관계를 임의 확정하지 않고 검토 필요로 남김 |

실적 조건·제외 조건도 어떤 혜택에 적용되는지 확인해야 합니다. 제목·참조 문구·표 구조에서 범위가 분명할 때 연결하고, 모든 공통 유의사항을 모든 혜택에 자동 적용하지 않습니다. 서버에는 관계와 근거, 미확정 사유를 함께 전달합니다.

형태만 맞는 정규화가 정확한 해석을 보장하지는 않습니다. 복잡한 조건이나 지원 밖 표현을 전부 자동 감지한다고 주장하지 않고, 확인한 처리 범위와 실패 사례를 남깁니다.

**완료 기준:** 같은 입력 구간에 같은 후처리를 적용할 수 있고, 정리한 값과 원문을 대조할 수 있습니다. 명시적 공유 관계와 불명확한 관계가 구분되어 서버·화면에 전달됩니다.

## 8. CPU에서 실행하고 다른 팀원이 재현할 수 있게 합니다

### DP-W1-06 로컬 실행부터 확인합니다

첫 주의 환경 목표는 **GPU 없이 문서 처리·규칙·후처리를 실행하는 것**입니다. 모델 학습과 최종 CPU 성능 검증은 손영원과 함께 준비하되, 로컬 LLM·GPU 서버 구축을 선행 조건으로 두지 않습니다.

1. OS·CPU·아키텍처·메모리와 실제 Python·라이브러리 버전을 기록합니다.
2. 입력 파일 위치와 출력 위치를 지정해 문서 처리·규칙·후처리를 실행합니다.
3. 같은 입력·설정에서 같은 조건 구간과 정리한 값을 얻는지 확인합니다.
4. 실패한 문서·블록과 이유를 정상 출력과 구분해 남깁니다.
5. 설치·실행·입출력 예시·지원 형식·남은 제약을 안내에 적습니다.
6. 다른 팀원 한 명이 안내를 보고 실행하거나 누락된 항목을 확인합니다.

구체적인 파일·함수 위치는 저장소 구조와 박서연의 연결 방식에 맞춰 정합니다. 처음에는 Python 함수나 로컬 실행 결과 파일로 연결해도 됩니다. 별도 추출 전용 서버까지 동시에 만들 필요는 없습니다. 실행한 명령만 재현 안내에 기록합니다.

Docker는 직접 실행이 확인된 뒤 의존성을 묶어 다른 환경에서 확인하는 추가 작업으로 진행합니다. 컨테이너는 실행 환경을 분리하는 데 사용하며, 장비·아키텍처·자원 차이까지 없애 주는 것은 아닙니다. [Docker 공식 안내](https://docs.docker.com/get-started/docker-concepts/the-basics/what-is-a-container/)

박서연과 데이터·DB 보관 경로를 맞추고 컨테이너를 다시 만들 때 결과가 사라지지 않는지 확인합니다. 이번 주에 Docker까지 완료하지 못하면 직접 실행 완료와 컨테이너 실행 미확인을 구분합니다. K8s나 클라우드 배포는 첫 주 필수 범위로 추가하지 않습니다.

**측정할 때 지킬 점**

- 파싱·규칙 실행·후처리·문서 전체 시간의 측정 범위를 적습니다.
- 모델 CPU 블록 시간은 손영원과 토큰화·추론·공통 후처리 구간을 맞춥니다.
- 모델 준비 실행 후 배치 1·256토큰 이하 블록의 p95 5초 목표를 문서 전체 목표로 바꾸어 설명하지 않습니다.
- 모델 로딩·문서 전체 시간·메모리는 별도 기록하고, 장비·스레드·반복 횟수·입력 버전을 함께 남깁니다.
- 모델이나 측정 도구가 준비되지 않았다면 미실행·미측정으로 남깁니다. 규칙 속도로 모델 성능을 대신 보고하지 않습니다.

## 9. 교수님 피드백과 예외 상황을 반영합니다

### 공정한 성능 비교를 위한 책임

규칙을 만드는 담당자로서 **규칙과 모델이 같은 문제를 풀고 있는지** 확인해야 합니다.

| 한글·이모지·줄바꿈이 포함됨 | 서버·화면이 같은 기준 문자열과 문자 단위로 근거 확인 |
| 연회비·이자율 등 범위 밖 숫자가 있음 | 혜택 조건으로 잘못 추출하는지 확인 |
| 실적 제외와 혜택 제외가 함께 있음 | 지침에 맞게 유형·범위 구분, 혼동 사례 기록 |
| 같은 금액·공유 한도·애매한 참조가 있음 | 명시적 관계만 연결하고 불명확한 범위는 검토 필요 |
| 찾지 못한 값·명시적 없음·0이 있음 | 값·상태·근거를 구분해 전달 |
| 같은 문서를 다시 처리하거나 버전이 바뀜 | 기존 식별·원본을 보존하고 입력·파싱 버전 변화를 추적 |

문자 위치·반복 문구·단위 변환·공유 관계는 작은 합성 사례로 반복 확인할 수 있게 남깁니다. 실제 파싱 품질은 원문과 대조한 결과를 별도로 기록합니다. 모든 미지원 표현이나 누락을 자동 감지하는 기능이 완성됐다고 가정하지 않습니다.

서버·화면이 아직 없으면 같은 샘플 파일로 형식과 위치를 확인합니다. 실제 API·브라우저 연결 완료와는 구분합니다. 모호한 주석·혜택 관계는 혼자 확정하지 않고 원문·블록 ID·판단 근거를 전달합니다.

| 막힌 상황 | 이번 주 대응 |
| --- | --- |
| 실제 자료를 아직 사용할 수 없음 | 합성 문서로 형식·규칙·계산 경로 확인, 실제 자료 검증은 미완료 |
| 특정 PDF·표가 제대로 읽히지 않음 | 실패 위치·이유 보존, 지원 입력을 좁히거나 다른 사용 가능한 공식 자료 검토 |
| 주석 경계가 계속 바뀜 | 손영원과 작은 사례부터 합의하고 텍스트·주석·규칙 버전 동시 확인 |
| 공통 형식이 미정임 | 최소 블록·구간 샘플을 먼저 합의하고 임시 형식 표시 |
| 모델·GPU가 준비되지 않음 | 파싱·규칙·공통 후처리·CPU 재현 작업 계속 |
| 시간이 부족함 | 자료·원문 대응·첫 연결 우선, Docker 확대·범용 OCR·대량 수집은 후순위 |

## 12. 다음 주로 넘어가기 위한 기준

- [ ] 학습용 파일럿 자료의 출처·이용조건 확인 상태와 개발 용도를 기록했습니다.
- [ ] 실제 블록 5~10개를 원문과 대조해 전달하고, 10개 이상 공동 주석을 위한 준비·미달 범위를 확인했습니다.
- [ ] 제목·표·각주 문맥과 보존 텍스트·원문 대응 기준을 설명할 수 있습니다.
- [ ] 서버·화면·모델이 쓸 공통 형식과 문자 단위가 합의됐습니다.
- [ ] 규칙이 유형·구간·원문 값을 출력하고, 처리·미확인 범위를 기록했습니다.
- [ ] 공통 후처리가 원문·정리한 값·명시적 관계·검토 필요를 구분합니다.
- [ ] CPU 실행 절차와 환경이 남아 있고, 실제 연결과 샘플 확인 범위가 구분됩니다.

이 기준과 PM의 주석·평가 준비 상태를 함께 보고 다음 주의 자료 확대·규칙 보완·모델 비교·환경 정리를 정합니다. 입력과 원문 대응이 불안정하면 그 부분부터 보완합니다. 실제 자료가 준비되지 않았다면 합성 예시만으로 데이터 구축 완료라고 판단하지 않습니다.
