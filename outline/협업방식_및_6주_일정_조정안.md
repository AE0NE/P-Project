## 1. 무엇을 바꾸는가

기존 계획은 화면 기획·UI/UX 설계·구현·실제 API 연동을 첫 주에 너무 압축했습니다. 디자인 착수에 필요한 업무 예시와 화면 기획도 PM이 먼저 제공해야 합니다.

다음 원칙으로 수정합니다.

- 주중 여러 차례의 정기 점검과 매일 진행 보고를 두지 않습니다.
- 주 1회 회의에서 결과를 함께 보고, 다음 주의 핵심 산출물을 정합니다.
- 박세렴의 첫 주 결과는 Figma 와이어프레임과 검토할 질문입니다. React 구현·실제 API 연동은 첫 주 필수 완료 기준에서 제외합니다.
- 박세렴의 목~일 작업을 시작할 수 있도록 PM은 화면 기획·업무 예시를 먼저 공유합니다.
- 화면 구조 검토와 UI 디자인 시간을 확보하고, 백엔드·데이터·평가 준비는 병행합니다.
- 이후 주의 세부 작업량은 주간 결과와 가용시간을 보고 조정합니다. 아래 6주 표는 전체 진행 기준입니다.

**일정 우선순위:** 이 조정안과 각 주간 계획의 수정된 목표를 우선합니다. 기존 상세 작업 목록의 일별 마감·주중 점검·첫 주 전체 연동 목표는 적용하지 않습니다. 세부 기술 내용은 후속 개발 참고로 보존합니다.

## 2. 최종 기능 범위를 줄입니다

| 영역 | 최종 최소 구현 범위 | 후순위 작업 |
| --- | --- | --- |
| 문서 선택 | 검토 화면 상단에서 등록된 상품·문서 버전 선택 | 독립 문서 관리 페이지, 복잡한 검색·업로드 관리 |
| 조건 검토 | 원문과 여섯 조건 확인, 근거 선택, 수정·저장·재조회 | PDF 위의 정밀 좌표 강조, 복잡한 편집 도구 |
| 상품 비교 | 저장한 두 상품의 선택 혜택을 같은 기준으로 보여주는 읽기 전용 표 | 다수 상품 대시보드, 순위·추천·복잡한 필터 |
| 내보내기 | 저장된 검토 결과의 CSV, 출처·상태·버전 포함 | 여러 형식의 보고서 생성 |
| 계정·승인 | 연구용 시연에 필요한 최소 식별·검토 상태 | 별도 회원가입·조직별 권한·복잡한 승인 화면 |

조건 검토를 중심 화면으로 만들고, 문서 선택과 두 상품 비교를 같은 작업 흐름에 넣습니다. 비교 기능은 프로젝트 목적에 필요하므로 최종 최소 기능에 남깁니다. 독립된 대형 비교 페이지까지 설계하지는 않습니다.

첫 CSV 구현은 저장한 한 문서의 결과를 대상으로 합니다. 두 상품을 함께 내보내는 기능은 기본 저장·비교가 확인된 뒤 여유를 보고 정합니다. 화면·CSV에서 미확인과 명시적 없음, 공유 한도, 할인·포인트 단위는 계속 구분합니다.

## 3. PM과 UI/UX 담당자의 책임을 구분합니다

| 손영원이 먼저 제공할 것 | 박세렴이 설계할 것 | 함께 결정할 것 |
| --- | --- | --- |
| 사용자·업무 목적·우선순위 | 화면 정보 구조와 시선·조작 흐름 | 첫 검토 흐름이 실제 업무 목적에 맞는지 |
| 입력·결과 예시와 조건 의미 | Figma 와이어프레임·상태별 표현 | 수정·미확인·저장·실패 상태의 의미 |
| 필수 기능·후순위 기능·완료 기준 | UI 스타일과 재사용 컴포넌트 | 합의한 범위와 구현 가능성 |

PM이 화면 요구사항 없이 모든 기획을 디자이너에게 넘기지 않습니다. 화면 기획 초안은 논의의 출발점으로 제공하고, 세부 배치·동선·컴포넌트는 박세렴의 Figma 작업과 팀 검토로 구체화합니다.

이번 주에는 [화면 기획 초안](화면기획_초안.md)과 함께 조건 검토·두 상품 비교의 구성 참고 그림을 제공합니다. 그림은 합성 자료를 사용한 구성 제안이며 확정 디자인이나 구현된 화면이 아닙니다.

## 4. 주 1회 회의를 운영하는 방법

회의 요일·시간은 팀이 정합니다. 박세렴의 집중 작업 결과를 검토할 수 있도록 일요일 작업 후 또는 다음 주 초를 후보로 검토하되, 현재 확정 일정으로 기록하지 않습니다.

회의 전에는 각자 아래 내용을 한 번 정리합니다. 매일 작성할 필요는 없습니다.

```text
1. 이번 주 결과와 링크:
2. 아직 남은 작업:
3. 막힌 이유·도움 또는 결정이 필요한 내용:
4. 다음 주 확보 가능한 시간과 제안할 핵심 작업:
```

회의는 40분 안팎을 출발점으로 삼습니다.

| 순서 | 확인할 내용 | 남길 결과 |
| --- | --- | --- |
| 현황 확인 | 각자 실제로 완료한 것과 미완료 항목 | 추정이 아닌 증거 기반 현황 |
| 결과 검토 | Figma·실행 화면·데이터·평가 결과 중 핵심 자료 | 필요한 수정과 합의 |
| 장애물 결정 | 다른 담당자에게 필요한 최소 입력·응답 | 담당자·전달할 결과·확인 시점 |
| 다음 주 계획 | 가용시간과 작업량 | 담당자별 핵심 산출물 1~2개 |

회의 중에는 디자인·API·데이터 문제를 모두 즉석에서 구현하려 하지 않습니다. 결정할 것과 추가로 확인할 것을 구분해 PM이 기록합니다.

### 회의 사이에 막히면

GitHub 이슈·공유 문서·Figma 코멘트 중 팀이 정한 곳 한 군데에 질문을 남깁니다. 긴급한 연결 문제는 필요할 때 비동기로 확인하되, 매일 정해진 시간에 응답해야 하는 방식으로 운영하지 않습니다.

질문에는 대상 링크·기대 동작·막힌 이유·가능한 제안을 함께 적습니다. 답을 기다리는 동안 합의한 범위에서 진행할 수 있는 작업을 계속합니다. 답이 없다는 이유로 변경안이 승인됐다고 판단하지 않습니다.

Figma 화면 검토와 데이터 형식 협의도 댓글로 의견을 모을 수 있습니다. PM이 결정을 정리해 다음 작업자가 찾을 수 있게 남깁니다.

## 5. 이번 주 11/2~11/8의 목표

| 담당자 | 이번 주 핵심 산출물 | 이번 주 필수에서 제외할 것 |
| --- | --- | --- |
| 손영원 | 화면 기획·업무 예시·범위 초안, 파일럿·주석·평가 기준 초안 | 완성된 모델과 정식 성능 결과 |
| 박세렴 | 목~일에 핵심 검토 화면의 Figma 와이어프레임·상태 표현·질문 목록 | React 핵심 기능 완성, 실제 API 연동·통합 완료 |
| 박서연 | 샘플 JSON·상태·위치 기준과 API·DB 구조 초안 | 프런트엔드 연결을 전제로 한 전체 흐름 완료 |
| 박신혁 | 자료 확보·이용조건 상태, 학습용 파일럿의 첫 블록·출처 대응 | 모든 문서 형식·여섯 유형의 완성된 규칙·전체 환경 구축 |

박서연은 여유가 있으면 합성 자료의 조회·저장 API를 독립적으로 실행하고, 박신혁은 작은 규칙 초안을 확인할 수 있습니다. 추가 진행분을 다른 담당자의 첫 주 의무로 바꾸지는 않습니다.

실제 자료가 준비되면 작은 독립 이중 주석을 시작합니다. 250~400개 블록·초기 이중 주석 30~50개는 전체 구축 목표이며 첫 주 확보 완료 수량으로 간주하지 않습니다.

PM은 목요일 작업 착수 전에 기획 자료와 예시를 전달하는 것을 우선합니다. 첫 정기회의에서는 와이어프레임을 함께 보며 다음 주에 구현할 핵심 구조를 정합니다. 회의가 다음 주 초에 잡히면 실제 검토 전에는 화면 구조 확정으로 기록하지 않습니다.

| 6주차 12/7~12/12 | 최종 오류 수정·표시 점검·시연 준비 | 실행 안내·공개 범위·평가 보고서·발표 준비 | 재현·시연·문서·성과물 확인, 내부 완료 |

2주차에 모든 화면을 완벽하게 디자인할 때까지 다른 개발을 멈추는 방식은 아닙니다. 핵심 화면 구조를 먼저 검토하고, 합의된 부분부터 UI·컴포넌트·구현을 진행합니다. 백엔드·데이터·모델은 같은 샘플 형식으로 병행합니다.

4주차 말에는 추가 기능보다 평가에 필요한 안정성을 우선합니다. 평가를 마지막 주에 몰지 않습니다. 평가 후 결과에 영향을 주는 수정이 발생하면 버전과 변경 내용을 기록하고 필요한 범위를 다시 검증합니다. 시험 결과에 맞춘 모델·규칙 조정을 최초의 독립 평가인 것처럼 보고하지 않습니다.

이 일정의 실현 가능성은 아직 확보되지 않은 자료와 각자의 가용시간에 달려 있습니다. 주간 회의에서 실제 결과를 보고 조정하되, 데이터 부족·연동 지연·평가 미완료를 숨기지 않습니다.

## 7. 성능 비교는 계속 두 축으로 유지합니다

1. 같은 입력·공통 후처리에서 문맥 규칙과 학습 모델의 수정 전 Strict Span Micro-F1을 비교합니다.
2. 수작업·규칙 도구·모델 도구의 시간과 최종 누락·중요 오류를 함께 비교합니다.

규칙 도구와 모델 도구는 같은 화면·기능을 사용합니다. 디자인 차이를 모델 효과로 세지 않습니다. 미확인을 늘려 오류만 줄이는 결과를 구분하도록 필수 항목의 분모·자동 채움률·수정량을 함께 확인합니다.

기존 목표인 추출 F1 0.80, 규칙 대비 절대 0.03 개선 도전 목표, 정해진 CPU 조건의 블록 p95 5초는 목표로 유지합니다. 모델 우수성과 업무시간 단축이 이미 확인됐다는 의미는 아닙니다.

## 9. 박세렴에게 전달할 답장 초안

> 세렴님, 자세히 의견 주셔서 감사합니다. 기존 계획에서 화면 기획과 UI/UX 설계에 필요한 시간을 충분히 반영하지 못한 부분이 있었습니다. 제가 사용자 흐름, 핵심 기능 범위, 조건 예시와 화면 구성 초안을 먼저 정리해서 공유하겠습니다. 이번 주 목표는 Figma 와이어프레임과 팀 검토로 조정하고, 실제 구현과 API 연동은 화면 구조를 확인한 뒤 진행하는 방향으로 바꾸겠습니다. 문서 선택은 검토 화면 안에 넣고, 상품 비교도 두 상품을 보는 간단한 표로 범위를 줄이겠습니다. 정기회의는 주 1회로 운영하고, 목~일 작업 가능 시간을 반영해 일별 점검 대신 주간 산출물 기준으로 함께 조율하겠습니다. 회의 요일과 시간도 팀 일정에 맞춰 정하겠습니다.

이 문구는 사용자가 직접 전달할 수 있는 초안이며, 팀원에게 발송하지 않았습니다.
