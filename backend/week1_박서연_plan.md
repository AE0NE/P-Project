## 1. 이번 주에 내가 맡는 역할

내 역할은 **문서 처리·조건 추출 결과를 화면에 전달하고, 사용자가 검토한 결과를 원문·최초 예측과 구분해 저장하는 것**입니다. 프런트엔드와 문서 처리·AI 모듈이 서로 다른 형식으로 개발되지 않도록 공통 데이터 형식의 초안을 만드는 일도 맡습니다.

예를 들어 사용자가 월 한도를 수정했을 때, 화면에서만 값이 바뀌면 검토 결과가 남지 않습니다. 반대로 수정값으로 최초 예측까지 덮어쓰면 모델이 처음 무엇을 맞히고 틀렸는지 평가할 수 없습니다. 서버는 두 결과를 구분해 보관하고, 다시 조회하거나 CSV로 내보낼 때 어떤 결과인지 명확히 알려줘야 합니다.

| 내가 책임질 일 | 다른 담당자와 나눌 일 |
| --- | --- |
| API·저장 형식 초안과 버전 관리 | 모든 담당자가 자기 모듈에서 사용할 수 있는지 확인 |
| 문서·원문 블록·추출 결과의 조회와 저장 | 박신혁: 문서 파싱·규칙 추출·원문 대응 정보 |
| 최초 예측과 사람의 수정 결과 분리 | 손영원: 모델 출력, 정답·평가에 필요한 정보 |
| 수정 결과 저장·재조회·CSV 제공 | 박세렴: 요청 호출, 화면 편집·오류 표시 |
| 서버 실행 안내와 API 연동 점검 | 박신혁: 공통 실행 환경·Docker 연동 |

조건을 찾아내는 모델이나 파서를 백엔드에서 새로 구현하는 것이 첫 업무는 아닙니다. 담당자가 제공한 결과를 공통 형식으로 받아 검증·저장·전달하는 연결 부분부터 만듭니다.

## 2. 이번 주 목표와 우선순위

> **문서 한 건의 원문·추출 결과를 서버에서 조회하고, 수정한 검토 결과를 DB에 저장한 뒤 다시 조회하여 CSV로 내보내는 흐름을 연결합니다.**

처음에는 직접 만든 합성 자료를 DB에 등록해 서버 동작을 확인할 수 있습니다. 실제 자료·규칙 출력이 준비되면 같은 형식으로 연결합니다. 합성 자료를 사용한 실제 서버 연동과 실제 공식 문서 처리 성공은 구분해서 기록합니다.

| BE-W1-02 | FastAPI 실행과 DB 초기 구조 | 실행 명령·버전, DB 생성·샘플 등록·재시작 확인 |

작업시간은 아직 확정하지 않았습니다. 날짜별 일정은 권장 배치이며, 이번 주 확보 가능한 시간을 PM과 확인한 뒤 조정합니다. 모델 준비가 늦어져도 형식·DB·저장 API는 독립적으로 진행할 수 있습니다.

### BE-W1-01 팀이 같은 결과를 주고받을 기준부터 작성합니다

먼저 프로젝트 README를 읽고 아래 흐름을 설명할 수 있는지 확인합니다.

```text
박신혁: 문서 → 원문 블록·위치 → 규칙 결과
손영원: 같은 입력 → 모델 결과·평가용 예측
                  ↓
```

규칙과 모델은 같은 입력·공통 후처리 조건에서 비교할 추출기입니다. 반드시 둘을 차례대로 호출하는 구조로 이해하지 않습니다. 최초 연결은 합성 샘플이나 규칙 출력으로 시작할 수 있습니다.

오늘은 전체 API를 구현하려 하기보다 다음 내용을 표와 샘플 한 건으로 정리합니다.

2. 조회 화면에 필요한 필드를 박세렴에게 확인합니다.
3. 박신혁에게 원문·위치·규칙 출력 예시를 요청합니다.
4. 손영원에게 라벨·평가용 원래 예측의 보존 기준을 확인합니다.

## 4. 공통 데이터 형식을 구체화합니다

### 무엇을 구분해서 저장해야 하는가

| 데이터 묶음 | 필요한 정보 | 구분하는 이유 |
| --- | --- | --- |
| 상품·문서 | 상품군 ID, 문서 ID, 출처, 버전·수집일·해시, 합성·실제 구분 | 같은 상품의 개정 문서와 개발 샘플을 혼동하지 않기 위해 |
| 원문 블록 | 블록 ID, 문서 ID, 보존 텍스트, 위치 단위, 확인 가능한 출처 위치 | 조건을 원문에서 다시 찾기 위해 |
| 추출 실행 | 실행 ID, 문서·입력 버전, 추출기 종류·버전, 후처리 버전, 처리 상태 | 같은 문서를 다른 규칙·모델로 실행한 결과를 구분하기 위해 |
| 최초 추출 결과 | 조건 ID·유형·원문 구간, 정리한 값·단위·연산자, 명시된 적용 관계 | 원래 예측과 조건 해석을 보존하기 위해 |
| 검토 결과 | 실행 ID, 검토 버전, 수정 결과·근거, 검토 상태, 저장 시각 | 누가 무엇을 검토한 결과인지 별도 이력으로 남기기 위해 |

수정 주체를 어떻게 표시할지도 팀과 정합니다. 로그인 시스템을 먼저 만들기보다 첫 시연에 필요한 식별 범위를 합의합니다. 식별 방식이 없는데 실제 사용자별 이력을 관리한다고 주장하지 않습니다.

첫 주부터 위 정보를 모두 별도 테이블로 나눌 필요는 없습니다. 문서·블록·실행·최초 결과·검토 버전의 핵심 연결을 구분하고, 복잡한 조건·관계 묶음은 검증한 JSON으로 보관하는 초안도 가능합니다. 실제 테이블과 필드 구성은 합의 후 기록합니다.

### 상태와 누락값을 먼저 합의합니다

| 구분 | 표현할 내용 | 지켜야 할 원칙 |
| --- | --- | --- |
| 처리 상태 | 미실행·처리 중·성공·실패 등 | 처리 실패를 조건이 없다는 뜻으로 반환하지 않음 |
| 조건 확인 상태 | 추출됨·미확인·명시적 없음·검토 필요 | 미확인과 원문에 명시된 없음을 구분 |
| 사람의 검토·승인 상태 | 사람이 검토한 단계 | 저장 성공만으로 승인 상태를 바꾸지 않음 |
| 검토 버전 | 특정 실행에 대해 저장한 결과의 순서 | 다른 실행·문서의 수정 결과와 섞지 않음 |

실제 필드명과 상태 값은 팀과 확정합니다. 한 필드에 처리 상태·조건 상태·검토 상태를 모두 넣지 않습니다. 편집 중·저장 중처럼 화면에서 관리할 상태도 DB의 검토 상태와 구분합니다.

값이 미확인이면 정규화 값은 비워 두고 상태를 함께 제공합니다. 숫자 0, 빈 문자열, `null`, 명시적 없음은 같은 뜻으로 취급하지 않습니다. 미확인 항목에 가짜 원문 구간을 만들거나, 모든 블록에 여섯 유형의 정답이 있다고 가정하지 않습니다.

조건의 혜택 소속과 공유 한도는 ID·명시적 연결 관계로 표현합니다. 같은 5천 원이 등장했다는 이유로 한도 ID를 합치지 않습니다. 불명확한 관계는 검토 필요로 남깁니다.

### 원문 위치 기준을 합의합니다

아래는 **형식 논의용 합성 예시**이며 현재 구현된 API 응답은 아닙니다. 위치 단위도 합의를 위한 제안입니다.

```json
{
  "run_id": "SYN-R001",
  "document_id": "SYN-D001",
  "data_origin": "synthetic",
  "block_id": "SYN-B001",
  "offset_unit": "unicode_code_point",
  "text": "편의점 10% 할인",
  "spans": [
    {"type": "TARGET", "start": 0, "end": 3, "text": "편의점"},
    {"type": "RATE", "start": 4, "end": 7, "text": "10%"}
  ]
}
```

0부터 시작하고 끝 위치는 포함하지 않는 예시입니다. `text[4:7]`은 `10%`입니다. 여섯 유형은 `TARGET`, `RATE`, `SPEND`, `LIMIT`, `SPEND_EXCL`, `BENEFIT_EXCL`을 사용합니다.

확인할 것은 위치 범위와 문자열의 일치뿐 아니라 **어느 기준 문자열의 위치인가**입니다. 박신혁·손영원과 보존 원문, 모델 입력에 붙인 제목·표 헤더, 원문 복원 대응을 확인합니다. 박세렴과는 한글·이모지가 섞여도 같은 구간을 찾는지 확인합니다. PDF 좌표와 문자 위치는 같은 정보로 취급하지 않습니다.

이 합성 예시에 실제 카드사 URL이나 문서 해시를 꾸며 넣지 않습니다. 합성 자료임을 표시하고, 실제 자료에는 확인한 출처·버전을 연결합니다.

**완료 기준:** 팀원들이 같은 샘플을 자신의 모듈에서 사용할 수 있고, 필수·선택 필드와 미정 항목을 설명할 수 있습니다. 확정한 스키마 버전을 기록하고 변경 시 함께 검토합니다.

## 5. 실행 환경과 DB를 구성합니다

### BE-W1-02 작은 로컬 서버부터 실행합니다

개발 위치는 저장소의 `backend/`입니다. 현재 확인한 폴더는 초기 골격이므로 기존 코드가 추가됐는지 다시 확인한 뒤 작업합니다.

| 기술 | 이번 주 사용 목적 | 선택 이유와 한계 |
| --- | --- | --- |
| Python · FastAPI | 조회·검토 저장·CSV API | Python 문서 처리·AI 모듈과 연결하고 API 스키마·문서화를 활용하기 위해. [공식 안내](https://fastapi.tiangolo.com/tutorial/body/) |
| Pydantic | 요청·응답 형식과 제약 검증 | 필드·타입을 명시하기 위해. 형식 검증이 금융 조건의 해석까지 보장하지는 않음. [공식 안내](https://pydantic.dev/docs/validation/latest/concepts/models/) |
| Uvicorn | 로컬 API 서버 실행 | 팀이 요청을 보내고 동작을 확인할 실행 과정에 사용 |
| SQLite · Python sqlite3 | 문서·결과·검토 버전 저장 | 별도 DB 서버 없이 파일로 저장하는 소규모 프로토타입에 사용. 실제 다중 사용자 운영은 추가 검증 필요. [공식 안내](https://docs.python.org/3/library/sqlite3.html) |
| Swagger UI·Postman 등 | 요청·응답 점검 | 화면이 준비되기 전에도 서버 기능을 직접 확인하기 위해 |

첫 주 DB 접근은 Python 표준 `sqlite3`로 시작할 수 있습니다. 이미 팀이 정한 ORM이 있다면 그 선택을 따르되, 새 도구 도입보다 저장·재조회 검증을 우선합니다. Docker는 박신혁과 로컬 실행이 확인된 뒤 연결하고, K8s·Redis·작업 큐는 지금 필수로 추가하지 않습니다.

1. Python·FastAPI·Pydantic 등 실제 설치 버전과 실행 명령을 기록합니다.
2. 서버 실행 확인용 API와 API 문서가 열리는지 확인합니다.
3. DB 파일 위치·생성 절차를 정하고, 서버 재시작 후 같은 DB를 여는지 확인합니다.
4. 직접 만든 샘플을 등록하는 로컬 초기화 절차를 준비합니다. 기존 데이터를 지우는 초기화와 샘플 추가를 구분합니다.
5. 프런트엔드 개발 주소·포트와 브라우저 요청 허용 범위를 박세렴과 맞춥니다.
6. 설치·실행·DB 초기화·확인 절차를 백엔드 안내에 남깁니다.

DB 작업은 매개변수 바인딩으로 값을 전달하고, 검토 저장 중 오류가 나면 일부만 저장되지 않도록 트랜잭션 범위를 정합니다. 연결·커밋·롤백 동작은 사용하는 Python 버전에서 직접 확인합니다. [Python sqlite3 안내](https://docs.python.org/3/library/sqlite3.html)

DB 파일·원본 문서·키는 저장소 관리 원칙에 맞춰 제외합니다. 첫 주의 로컬 시연을 외부 공개 서비스 배포 완료로 기록하지 않습니다.

**완료 기준:** 서버를 껐다 켜도 등록한 샘플과 저장한 검토 결과가 남는지 확인할 수 있고, 다른 팀원이 안내를 보고 실행하거나 누락 사항을 확인했습니다.

## 6. 먼저 연결할 API를 정합니다

### BE-W1-03 조회부터 화면과 맞춥니다

아래 경로는 **팀 합의를 위한 초안**입니다. 기존에 합의한 형식이 있다면 확인 후 맞추며, 이 문서 작성만으로 확정된 API가 되는 것은 아닙니다.

| 우선순위 | 요청 초안 | 역할 | 첫 확인 기준 |
| --- | --- | --- | --- |
| 필수 | `GET /health` | 서버 실행 확인 | 응답을 받되 이것만으로 DB·모델 정상까지 주장하지 않음 |
| 필수 | `GET /api/documents` | 등록 문서와 연결된 실행 목록 조회 | 문서·버전·합성 여부·실행 ID 구분 |
| 필수 | `GET /api/runs/{run_id}` | 원문 블록·최초 예측·최신 검토 결과 조회 | 화면이 근거와 수정값을 구분해 표시 가능 |
| 필수 | `POST /api/runs/{run_id}/reviews` | 새 검토 버전 저장 | DB 저장 후 버전·저장 시각·결과 반환 |
| 필수 | `GET /api/runs/{run_id}/reviews/{revision}/export.csv` | 지정 검토 버전의 CSV | 저장된 버전과 파일 내용 일치 |
| 후순위 | 문서의 새 추출 실행 요청 API | 파서·규칙·모델 호출 | 실제 실행 모듈과 실패 상태가 준비되면 경로 확정 |

최초 시연은 로컬 등록 절차로 합성·규칙 결과를 넣고 조회 API부터 연결해도 됩니다. 파일 업로드·URL 자동 수집·분석 요청 화면까지 한 번에 구현할 필요는 없습니다. 새 실행 API가 없다면 그 상태를 기록하고, 등록된 결과 조회와 새 분석 실행을 구분합니다.

조회 응답에는 문서·실행 식별자, 보존 원문·위치 정보, 최초 추출 결과, 최신 저장 검토 결과를 구분해서 제공합니다. 검토가 아직 없으면 그 사실을 명시합니다. 최초 예측을 이미 검토한 값처럼 복사해 저장하지 않습니다.

**실제 모듈을 연결할 때 확인할 것**

1. 박신혁의 파싱·규칙 출력이 공통 형식으로 들어오는지 확인합니다.
2. 입력 문서·블록과 결과의 ID가 일치하는지 확인합니다.
3. 조건 유형, 문자 범위, 해당 범위의 원문 값이 맞는지 검증합니다.
4. 입력에 붙인 제목·헤더와 보존 원문 사이의 위치 대응을 확인합니다.
5. 실행 실패나 유효하지 않은 결과를 정상 결과로 조용히 바꾸지 않고 사유를 기록합니다.
6. 실제 규칙·모델 실행과 합성 응답을 실행 정보에서 구분합니다.

Pydantic은 선언한 형식과 제약을 검사하는 데 사용합니다. 같은 문서의 블록인지, 범위가 문자열 안에 있는지, 공유 한도 연결이 유효한지 등 프로젝트의 검증 규칙은 별도로 작성해야 합니다. 입력값의 자동 형변환과 추가 필드 처리도 정해, 잘못된 값이 모르게 통과하지 않게 합니다.

모델 실행 기능이 아직 없으면 없다고 반환합니다. 모델을 요청했는데 내부에서 규칙으로 바꿔 놓고 모델 결과라고 저장하지 않습니다. 실제 모델 연결은 손영원의 출력과 환경이 준비되면 같은 입출력 형식에 맞춰 추가합니다.

반복 개발·통합에 사용할 실제 자료는 손영원이 학습용으로 지정한 파일럿을 사용합니다. 최종 시험 자료를 API 디버깅이나 데모 개선에 반복 사용하지 않습니다. 같은 상품의 문서·개정본이 어느 상품군에 속하는지도 함께 보존합니다.

**완료 기준:** 박세렴의 화면에서 서버의 같은 실행 ID를 조회하고, 원문·최초 예측·검토 유무를 올바르게 표시합니다. 합성·규칙·모델 중 무엇으로 확인했는지 남깁니다.

## 7. 수정값을 안전하게 저장하고 다시 조회합니다

### BE-W1-04 최초 예측을 바꾸지 않는 검토 저장

첫 주에는 변경된 필드만 처리하는 복잡한 방식보다 **검토 대상 결과 전체를 하나의 검토 버전으로 저장하는 방식**을 초안으로 삼습니다. 실제 요청 형식은 박세렴과 맞춥니다.

```text
추출 실행 SYN-R001
  ├─ 최초 예측: 원래 출력 보존
  ├─ 검토 버전 1: 첫 수정 결과
  └─ 검토 버전 2: 추가 수정 결과

재분석한 다른 실행은 별도 실행 ID로 관리
```

1. 요청의 실행 ID와 수정 대상 조건·혜택·근거가 같은 문서에 속하는지 확인합니다.
2. 수정값·조건 확인 상태·검토 상태를 검증합니다.
3. 새 검토 버전을 저장합니다. 최초 예측이나 이전 검토 버전을 덮어쓰지 않습니다.
4. 저장이 끝난 뒤 검토 버전·저장 시각·저장 결과를 응답합니다.
5. 조회 API로 다시 읽어 같은 값이 남는지 확인합니다.
6. 새 문서 버전이나 새 추출 실행에는 이전 승인을 자동으로 이어 붙이지 않습니다.

사용자가 정규화 값을 수정했다고 보존 원문까지 바꾸지 않습니다. 원문 구간을 수정하는 기능을 제공한다면 그 위치·문구가 일치하는지도 확인합니다. 근거 없는 값을 근거 확인 완료나 명시적 없음으로 처리하지 않습니다. 다만 형식 검증만으로 사용자의 해석이 참인지 자동 보장할 수는 없으므로, 검토 판단과 근거를 구분해 남깁니다.

같은 버전을 바탕으로 저장 요청이 겹칠 때 덮어쓰지 않도록, 요청에 `base_revision`을 포함하는 방식을 제안합니다. 검토가 없을 때는 0, 최신 검토가 1이면 1을 보내도록 정할 수 있습니다. 서버는 최신 버전 확인과 새 버전 저장을 같은 트랜잭션 안에서 처리하고, 오래된 버전이면 409 응답으로 재조회를 안내합니다.

저장은 성공했는데 응답이 유실될 수도 있습니다. 이때 프런트엔드가 재조회해 실제 저장 여부를 확인할 수 있어야 합니다. 같은 요청을 다시 보냈을 때 새 버전이 중복 생성되거나 이전 결과를 덮어쓰지 않는지 확인합니다. 이 방식의 세부 규약은 박세렴과 함께 확정합니다.

저장 중 오류가 나면 일부 조건만 바뀌지 않도록 롤백합니다. 성공 응답은 DB 저장이 완료된 뒤 반환합니다. 저장과 검토·승인은 별도 동작이며, 승인 절차가 미정이면 저장 기능부터 구현하고 승인 API는 미구현으로 남깁니다.

**완료 기준:** 값을 수정해 저장한 뒤 재조회·서버 재시작에서도 수정 결과가 남고, 최초 예측과 이전 검토 버전이 보존됩니다. 실패 요청에는 성공으로 응답하지 않습니다.

## 8. 검토한 결과를 CSV로 내보냅니다

### BE-W1-05 어떤 버전의 조사표인지 남깁니다

CSV는 화면의 미저장 초안이 아니라 **지정한 실행·검토 버전의 저장 결과**에서 만듭니다. 파일을 만드는 동안 최신 검토가 바뀌더라도 요청한 버전의 내용을 내보냅니다. 존재하지 않는 버전은 오류로 응답하고 다른 버전으로 임의 대체하지 않습니다.

첫 주에는 혜택·조건별로 행을 만드는 형식을 초안으로 정하고, 박세렴·손영원과 열 구성을 확인합니다.

| 포함할 묶음 | 열에 남길 내용 |
| --- | --- |
| 자료 식별 | 상품·문서 ID, 문서 버전, 실행 ID, 검토 버전, 합성·실제 구분 |
| 조건 | 혜택·조건 ID, 유형, 원문 값, 정규화 값, 단위·연산자·기간 |
| 적용 범위 | 명시된 혜택 연결·공유 한도 ID와 범위, 확인 상태 |
| 검토 | 조건 확인 상태, 사람의 검토 상태 |
| 근거 | 출처 URL, 블록 ID, 확인 가능한 원문 위치·페이지 |

미확인은 값 칸을 비워도 상태 칸에 남깁니다. 명시적 없음·숫자 0과 구분할 수 있어야 합니다. 한도가 공유되면 각 행에 같은 그룹 참조를 보존해 독립 한도로 오해하지 않게 합니다. 포인트를 원화로 자동 환산하거나 상품 전체 순위를 생성하지 않습니다.

쉼표·따옴표·줄바꿈이 들어간 원문도 열이 틀어지지 않도록 Python `csv` 모듈로 작성합니다. 빈 값만으로 의미를 구분할 수 없으므로 별도 상태 열을 유지합니다. [Python CSV 안내](https://docs.python.org/3/library/csv.html)

박세렴과 파일명·응답 형식·다운로드 방식을 맞추고, 한글이 깨지는지 실제 사용 환경에서 확인합니다. 파일을 다시 읽어 행·열과 저장 결과가 일치하는지도 확인합니다. 합성 자료의 빈 출처에 실제 카드사 URL을 채워 넣지 않습니다.

**완료 기준:** 특정 검토 버전을 내보내고, 저장한 값·상태·출처·공유 관계와 파일 내용이 일치함을 확인했습니다. 다운로드 성공과 내용 검증 성공을 각각 기록합니다.

## 9. 예외 상황과 확인 방법

### BE-W1-06 저장·원문·API의 실제 동작을 확인합니다

아래는 첫 주 기능이 준비되면 확인할 핵심 사례입니다. 숫자만 맞추기 위한 테스트 수를 만들기보다 저장 무결성과 화면 연동을 실제로 확인합니다.

| 점검 상황 | 기대 동작과 확인할 증거 |
| --- | --- |
| 등록한 뒤 서버를 재시작함 | 같은 DB에서 문서·원문·검토 결과 조회 가능 |
| 검토값을 수정해 저장함 | 재조회 결과는 수정값, 최초 예측과 이전 검토는 그대로 유지 |
| 저장 도중 오류가 발생함 | 일부만 저장되지 않고, 이전 버전 유지·실패 응답 |
| 오래된 검토 버전으로 저장함 | 충돌 응답, 최신 결과 덮어쓰기 없음 |
| 저장 응답 유실 후 재시도함 | 재조회로 결과 확인 가능, 중복 버전·조용한 덮어쓰기 방지 |
| 미확인·명시적 없음·0이 각각 들어옴 | 조회·저장·CSV에서 의미 구분 유지 |
| 잘못된 라벨·범위·다른 문서 ID가 들어옴 | 입력 거절 또는 실행 오류로 기록, 정상 근거로 반환하지 않음 |
| 이모지·제목·표 헤더가 포함됨 | 합의한 위치 단위·기준 문자열로 원문 대조 가능 |
| 같은 금액 또는 공유 한도가 들어옴 | 금액으로 임의 병합하지 않고 명시된 관계 보존 |
| 추출 결과가 비었거나 실행이 실패함 | 정상 빈 결과와 실행 실패를 구분, 없음으로 자동 확정하지 않음 |
| CSV에 한글·쉼표·따옴표·줄바꿈이 있음 | 다시 읽어도 행·열·상태·검토 버전이 맞음 |
| 브라우저에서 조회·저장·내보냄 | 문서 도구에서만 성공한 것과 구분해 실제 화면 요청 확인 |

핵심 저장·버전 충돌·원문 위치·CSV 사례는 반복 실행 가능한 작은 검증으로 남깁니다. 응답·로그에는 합성 여부와 코드·스키마 버전을 기록하고, 공개 자료에는 키·개인정보·이용 범위를 확인하지 않은 원문을 넣지 않습니다.

**오류 응답도 프런트엔드와 합의합니다.** 다음은 상태 코드 사용 초안입니다.

| 상황 | 응답 초안 | 화면이 알 수 있어야 할 것 |
| --- | --- | --- |
| 문서·실행·검토 버전이 존재하지 않음 | 404 | 어떤 대상을 찾지 못했는지 |
| 요청 필드·라벨·원문 위치가 유효하지 않음 | 422 | 문제가 된 항목과 수정할 내용 |
| 검토 버전 충돌·처리 상태가 요청과 맞지 않음 | 409 | 다시 조회하거나 선행 처리가 필요한지 |
| 요청한 추출 기능·필수 모듈이 준비되지 않음 | 503 | 준비되지 않은 기능과 재시도 가능 여부 |
| 예상하지 못한 저장·처리 오류 | 500 | 실패 사실과 확인용 요청 ID |

입력 요청의 오류와 서버 내부 추출 결과의 오류는 구분합니다. 내부 모듈 오류를 사용자 입력 오류로 돌리지 않습니다. 실패 원인을 알 수 있는 서버 기록을 남기되, 화면에는 내부 경로·긴 예외 추적을 그대로 보여주지 않습니다.

## 10. 성능 비교를 위해 백엔드에서 지킬 점

교수님이 요구한 규칙·모델 비교가 가능하려면, 서버가 어떤 결과를 어떤 조건에서 만들었는지 보존해야 합니다.

- 규칙과 모델은 같은 입력·공통 후처리 조건을 사용하고, 같은 응답 형식으로 전달합니다.
- 실행별로 입력·추출기·후처리·스키마 버전을 남깁니다. 아직 없는 버전값을 임의로 만들지 않습니다.
- 수정 전 예측과 검토 후 결과를 분리해, 손영원이 원래 예측을 평가할 수 있게 합니다.
- 처리 실패·보류 건을 조용히 빼서 성능이 높아 보이게 하지 않습니다. 대상·실패 수를 함께 전달합니다.
- 모델 요청을 규칙으로 대체하거나 캐시 결과를 새 추론 결과처럼 기록하지 않습니다.
- 같은 문서의 규칙 실행·모델 실행과 각 검토 이력을 실행 ID별로 구분합니다.

Strict Span Micro-F1 계산과 최종 평가 설계는 손영원이 담당합니다. 백엔드는 원래 구간·유형·입력 버전을 보존하고, 평가용 결과를 꺼낼 수 있게 협의합니다. 사람의 정답·수정값을 최초 예측에 섞지 않습니다.

CPU 블록 처리시간 목표는 모델 준비 실행 후 토큰화·추론·공통 후처리를 측정하는 기준입니다. HTTP 요청·DB·문서 전체 처리시간과 다른 측정이므로, API 응답시간을 모델의 p95로 보고하지 않습니다. 측정 구간은 손영원·박신혁과 맞춥니다.

수작업·규칙 도구·모델 도구의 업무 비교는 이후 같은 화면·기능과 과제 기준으로 진행합니다. 이번 주에는 필요한 결과·버전이 보존되는지 확인하며, 업무시간 단축이나 모델 우수성은 아직 측정 성과로 작성하지 않습니다.
