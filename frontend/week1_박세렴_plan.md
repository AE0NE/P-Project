## 1. 이번 주에 내가 맡는 역할

내 역할은 **추출된 조건을 사용자가 원문과 대조하고, 잘못된 부분을 수정해 저장할 수 있는 화면을 만드는 것**입니다. 숫자를 보기 좋게 나열하는 것만으로는 이 프로젝트의 문제를 해결할 수 없습니다. 어떤 조건이 어디에서 나왔고, 아직 확인하지 못한 부분은 무엇인지 화면에서 구분할 수 있어야 합니다.

예를 들어 편의점과 카페가 월 5천 원 한도를 공유한다면, 각 혜택에 별도 한도가 있는 것처럼 보이지 않게 표시해야 합니다. 다만 공유 여부를 프런트엔드가 추측해서 결정하지는 않습니다. 서버가 전달한 연결 관계를 보여주고, 불명확하면 검토가 필요하다고 표시합니다.

| 내가 책임질 일 | 다른 담당자에게 받아 연결할 일 |
| --- | --- |
| 원문·조건을 함께 보는 화면과 선택 동작 | 박신혁: 문맥 블록, 원문 위치와 출처 정보 |
| 조건값·상태 표시, 수정·저장·오류 안내 | 박서연: 조회·수정 저장·CSV API와 데이터 형식 |
| 검토에 필요한 항목과 사용 흐름 구현 | 손영원: 여섯 조건의 의미, 검토 과제와 완료 기준 |
| 임시 데이터와 실제 연동 범위 구분 | 팀 공동: 공통 샘플, API 계약, 통합 확인 |

모델 학습이나 규칙 구현을 기다릴 필요는 없습니다. 합의한 형식의 임시 응답으로 화면을 먼저 만들고, 실제 서버가 준비되면 같은 화면에 연결합니다.

첫 주에는 한 문서의 검토 흐름을 우선합니다. 여러 상품의 비교표는 이 흐름이 연결된 뒤 진행할 추가 작업으로 둡니다. 챗봇·카드 추천·실제 할인액 계산은 이번 작업 범위에 포함하지 않습니다.

## 3. 오늘 바로 시작할 일

### FE-W1-01 사용자가 할 일을 먼저 그립니다

README를 읽은 뒤 다음 흐름을 종이나 간단한 화면 스케치로 만듭니다. 완성된 디자인 도구나 별도 디자인 시스템부터 만들 필요는 없습니다.

```text
문서 선택
   ↓
원문과 추출 조건을 나란히 확인
   ↓
조건 선택 → 해당 원문 근거 확인
   ↓
조건 수정 → 변경 내용 저장
   ↓
다시 조회해 저장 결과 확인 → CSV 내보내기
```

첫 화면은 아래 네 부분으로 구성합니다.

| 화면 영역 | 첫 주에 보여줄 내용 | 필요한 이유 |
| --- | --- | --- |
| 문서 정보 | 상품명, 문서 버전·출처, 선택 문서 | 서로 다른 상품·개정본의 결과를 혼동하지 않기 위해 |
| 원문 영역 | 보존한 블록 텍스트, 제목·표 문맥, 확인 가능한 위치 | 추출값이 어떤 문맥에서 나왔는지 대조하기 위해 |
| 조건 영역 | 여섯 조건, 원문 값·정리한 값, 확인 상태 | 비율 외에 실적·한도·제외 조건도 검토하기 위해 |
| 작업 영역 | 수정·취소·저장, 저장 상태, 내보내기 | 검토 결과가 실제로 남았는지 알 수 있게 하기 위해 |

원문은 왼쪽, 조건은 오른쪽에 배치하는 구성을 출발점으로 삼되 노트북 화면에서 읽고 수정할 수 있는지 확인합니다. 작은 화면에서는 세로로 배치할 수 있으며, 별도 모바일 앱은 만들지 않습니다.

**오늘 남길 결과**

- [ ] 내가 이해한 사용자·문제·첫 시연 흐름을 짧게 정리했습니다.
- [ ] 원문과 조건을 함께 보는 화면 스케치를 만들었습니다.
- [ ] 여섯 조건을 모두 표시할 자리가 있습니다.
- [ ] 미확인·검토 필요와 저장 상태가 어디에 보일지 정했습니다.
- [ ] 손영원·박서연과 화면에 필요한 데이터가 무엇인지 확인할 목록을 만들었습니다.

## 4. 화면 개발을 시작하는 방법

### FE-W1-02 기존 역량으로 실행 환경을 구성합니다

개발 위치는 저장소의 `frontend/`입니다. 현재 확인한 폴더에는 초기 표시 파일만 있으므로, 기존 구현이 있는지 다시 확인한 뒤 시작합니다. 다른 사람이 만든 코드를 덮어쓰지 않습니다.

| 기술 | 이번 주 사용 목적 | 선택 이유와 사용 범위 |
| --- | --- | --- |
| React · TypeScript · Vite | 검토 화면과 개발 환경 | 기존 경험을 활용하고, 응답 데이터와 컴포넌트 입력을 명확히 표현하기 위해 |
| Tailwind CSS 또는 기존 CSS 방식 | 두 영역 배치와 상태 표시 | 익숙한 방식으로 읽기 쉬운 화면을 먼저 만들기 위해. 새 UI 라이브러리 도입은 필수가 아님 |
| Axios | 서버 요청을 모으는 API 함수 | 요청 경로·오류 처리를 컴포넌트에서 분리하기 위해 |
| React Query | 서버 결과 조회와 저장 후 갱신 | 서버에서 받은 결과와 화면의 로딩·실패 상태를 관리하기 위해 |
| useState 등 React Hooks | 선택 조건과 편집 중인 값 | 서버에 저장된 값과 아직 저장하지 않은 수정 초안을 구분하기 위해 |

첫 주에는 한 검토 화면으로 시작할 수 있습니다. 여러 페이지가 필요해질 때 React Router를 연결하고, 별도 전역 상태 관리 도구는 필요한 이유가 생긴 뒤 검토합니다.

1. 팀에서 사용할 Node·패키지 관리 도구와 실제 버전을 기록합니다.
2. 개발 서버 실행, 타입 검사·빌드 방법을 확인합니다.
3. 설치·실행 명령을 프런트엔드 안내에 남깁니다.
4. 의존성 목록과 사용하는 잠금 파일을 함께 관리합니다.
5. 서버 주소 설정은 한곳으로 모으고, 실제 비밀값이 없는 설정 예시만 공유합니다.

**완료 기준:** 다른 팀원 한 명이 안내를 보고 첫 화면을 실행하거나, 실행에 필요한 누락 항목을 함께 확인했습니다. 명령은 실제로 실행한 결과를 기준으로 기록합니다.

### FE-W1-03 공통 형식을 확인하고 임시 응답을 준비합니다

API 형식 초안은 박서연이 작성하고, 박세렴은 화면 구현에 필요한 정보가 있는지 확인합니다. 확정 전 임시 타입을 만들 수 있지만, 이를 팀이 합의한 최종 규약으로 기록하지 않습니다.

| 데이터 묶음 | 화면에서 필요한 정보 | 함께 확인할 담당자 |
| --- | --- | --- |
| 문서 | 상품·문서 ID, 출처 URL, 문서 버전·수집일 | 박서연·박신혁 |
| 원문 근거 | 블록 ID, 보존 텍스트, 확인 가능한 페이지·위치, 문자 기준 | 박신혁·손영원 |
| 조건 | 조건 ID, 여섯 유형, 원문 값·정규화 값, 단위·연산자 | 박서연·손영원 |
| 적용 관계 | 혜택 ID, 혜택 종류, 한도 공유 관계와 확인 상태 | 박서연·박신혁 |
| 검토 결과 | 최초 예측, 저장된 수정 결과, 검토 상태 | 박서연·손영원 |
| 요청 결과 | 저장 성공 시 반환값, 실패 응답, CSV 응답 방식 | 박서연 |

여섯 유형은 `TARGET`, `RATE`, `SPEND`, `LIMIT`, `SPEND_EXCL`, `BENEFIT_EXCL`입니다. 화면에서는 각각 대상·혜택 비율·전월 실적·혜택 한도·실적 제외·혜택 제외로 표시합니다.

처음에는 PM 계획과 같은 **직접 만든 합성 문장**을 사용할 수 있습니다.

```text
블록 ID: SYN-B001
보존 텍스트: 편의점 10% 할인
TARGET: 시작 0, 끝 3 → 편의점
RATE: 시작 4, 끝 7 → 10%
```

시작은 0부터 세고 끝은 포함하지 않는 예시입니다. 문자 단위는 팀과 별도로 합의해야 합니다. 이 예시는 실제 카드 조건이나 모델 성능을 뜻하지 않습니다.

임시 응답은 API 함수 뒤에서 제공하도록 구성합니다. 컴포넌트마다 별도 하드코딩을 넣기보다, 같은 타입의 응답을 한곳에서 받아 그리게 만듭니다. 실제 API 전환 시 화면을 다시 만들지 않도록 하기 위한 것입니다. 화면에도 **개발용 합성 데이터**라고 표시합니다.

추가 합성 사례는 정상 결과, 미확인 조건, 명시적 없음, 공유 한도, 모호한 관계, 빈 결과를 구분해 준비합니다. 금액이 같다는 이유로 같은 한도라고 묶는 사례는 만들지 않습니다. 공개할 예시는 직접 만든 내용으로 구성합니다.

**완료 기준:** 팀이 같은 샘플을 보고 필드·누락값·상태를 설명할 수 있고, 형식이 바뀔 때 확인할 담당자가 정해져 있습니다.

## 5. 원문을 확인할 수 있는 검토 화면을 만듭니다

### FE-W1-04 조건 선택과 근거 표시

첫 주에는 보존한 원문 블록을 그대로 보여주고, 선택한 조건의 근거 구간을 강조하는 방식부터 구현합니다. PDF 위에 정밀한 사각형을 그리는 뷰어는 별도 좌표 정보가 필요하므로 첫 흐름의 필수 기능으로 두지 않습니다.

1. 조건을 선택하면 대응하는 원문 블록을 보여줍니다.
2. 위치 대응이 유효하면 해당 문자열을 강조합니다.
3. 원문 값과 정규화 값을 구분해 표시합니다. 예를 들어 `30만 원 이상`과 `300000원, 이상`은 용도가 다릅니다.
4. 페이지 정보가 있으면 표시하고, 없으면 임의의 페이지를 채우지 않습니다.
5. 위치 대응이 없거나 틀리면 정확히 강조했다고 표시하지 않고, 블록과 출처를 제공하며 확인이 필요하다고 안내합니다.

**원문 강조에서 먼저 확인할 점**

- 브라우저에서 보여주는 기준 문자열과 서버의 위치 기준 문자열이 같은지 확인합니다. 화면에서 공백·줄바꿈·한글 정규화를 임의로 바꾼 뒤 기존 위치를 적용하면 안 됩니다.
- Python과 JavaScript는 문자열 위치를 세는 방식이 달라질 수 있습니다. 한글뿐 아니라 이모지가 섞인 합성 문장으로 같은 구간이 선택되는지 확인합니다.
- Unicode 코드 포인트 단위로 합의했다면 브라우저도 그 기준으로 변환해 처리합니다. JavaScript 문자열의 기본 위치를 그대로 같은 단위라고 가정하지 않습니다.
- 모델 입력에 붙인 제목·헤더의 위치를 PDF 본문 위치로 바로 사용하지 않습니다. 박신혁과 보존 원문으로 돌아가는 대응을 확인합니다.
- 원문 텍스트를 HTML 코드로 실행하는 방식 대신 텍스트로 표시하고, 강조할 구간만 화면 요소로 나눕니다.

**상태는 다음처럼 구분합니다.** 실제 API 필드명과 값은 박서연과 확정합니다.

| 구분 | 화면에서의 의미 | 주의할 점 |
| --- | --- | --- |
| 조건 확인 상태 | 추출됨·미확인·명시적 없음·검토 필요 | 미확인을 없음이나 0으로 바꾸지 않음 |
| 사람의 검토·승인 상태 | 사람이 어디까지 검토했는지 | 값이 있다는 이유로 검토 완료라고 표시하지 않음 |
| 저장 상태 | 변경 없음·미저장 변경·저장 중·저장 성공·저장 실패 | 저장 성공을 승인 완료로 취급하지 않음 |

숫자 0, 값 없음, 미확인은 구분해야 합니다. 표시 과정에서 0을 빈 값으로 바꾸지 않습니다. 원문에 명시된 없음도 근거를 함께 확인할 수 있어야 합니다. 검토한 결과에 미확인이 남아 있으면 그 상태를 숨기지 않습니다.

공유 한도는 서버가 명시한 공통 한도나 그룹을 기준으로 표시합니다. 수정 권한과 저장 규약이 정해지기 전에는 관계를 임의로 바꾸는 기능을 추가하지 않습니다. 할인과 포인트, 원과 포인트도 근거 없이 같은 단위로 환산하지 않습니다.

**완료 기준:** 합성 예시에서 여섯 조건과 상태를 표시하고, 선택한 조건의 근거를 찾을 수 있습니다. 실제 자료로 확인했는지는 별도로 기록합니다.

## 6. 수정·저장·내보내기를 연결합니다

### FE-W1-05 화면의 수정값과 서버 저장값을 구분합니다

편집은 다음 세 정보를 분리하는 구조로 시작합니다.

```text
최초 추출 예측: 읽기 전용으로 보존
저장된 검토 결과: 서버에서 조회한 현재 결과
편집 중 초안: 아직 저장하지 않은 화면의 변경 내용
```

1. 저장된 검토 결과를 기준으로 편집 초안을 만듭니다. 검토 결과가 없으면 서버가 정한 초기 표시 규약을 따릅니다.
2. 사용자가 바꿔도 최초 예측은 덮어쓰지 않습니다.
3. 취소하면 마지막 저장 상태로 돌아가며, 최초 예측과 같다고 가정하지 않습니다.
4. 저장 중에는 중복 제출과 추가 편집을 막는 방식으로 요청 대상 값을 분명히 합니다.
5. 서버가 성공을 반환한 뒤 결과를 다시 조회하고, 실제 저장된 내용을 보여줍니다.
6. 실패하면 변경한 초안을 남겨 재시도할 수 있게 합니다. 성공 메시지는 띄우지 않습니다.

조회한 서버 데이터는 React Query로 관리하고, 편집 초안과 선택 항목은 별도 화면 상태로 관리하는 구성을 사용합니다. 조회 캐시를 직접 바꿔 놓고 저장됐다고 판단하지 않습니다. 새로고침하거나 화면을 다시 열어도 같은 수정 결과가 남는지 박서연과 확인합니다.

문서를 바꾸거나 화면을 이동할 때 미저장 변경이 있으면 저장·취소 여부를 확인하도록 합니다. 승인 버튼은 승인 요청과 상태 전환 규약까지 합의된 경우에 추가합니다. 첫 주에는 저장 기능을 우선하며, 저장만으로 승인 상태를 바꾸지 않습니다.

### FE-W1-06 실제 API와 CSV를 연결합니다

박서연과 다음 기능별로 임시 응답인지 실제 API인지 확인합니다.

| 연결 기능 | 실제 연동 완료 기준 |
| --- | --- |
| 문서·결과 조회 | 선택한 문서의 실제 서버 결과를 화면에 표시 |
| 수정 저장 | 저장 요청 후 재조회·새로고침에서도 수정 결과 유지 |
| 최초 예측 확인 | 수정 후에도 원래 예측을 구분해 확인 |
| CSV 내보내기 | 서버가 생성한 파일을 받아 내용·상태·출처를 확인 |

CSV는 서버에 저장된 검토 결과를 기준으로 내보내도록 맞춥니다. 미저장 변경이 있으면 먼저 저장하도록 안내합니다. 미확인과 검토 상태, 출처가 CSV에 남는지도 함께 확인합니다. 버튼이 눌리거나 파일이 내려받아졌다는 사실만으로 내용까지 맞는 것으로 기록하지 않습니다.

백엔드가 준비되지 않았다면 임시 응답으로 화면 동작을 확인하고, 실제 저장·CSV는 미연동으로 남깁니다. 브라우저 내부의 임시 저장이나 직접 만든 CSV는 화면 시연에는 사용할 수 있지만 서버 저장·서버 CSV 완료 증거로 세지 않습니다.

**추가 비교 화면은 여유가 있을 때만 진행합니다.** 같은 형식의 두 상품을 나란히 보여주는 읽기 전용 초안부터 만들고, 비교 순위·추천 점수는 추가하지 않습니다. 한 문서의 검토·저장 흐름이 막혀 있다면 이 작업보다 먼저 해결합니다.

## 7. 첫 주에 확인할 예외 상황

다음은 기능이 연결되면 직접 실행해 볼 점검 목록입니다. 결과는 성공·실패·미확인으로 기록하고, 해당 화면이나 요청 결과를 남깁니다.

| 점검 상황 | 기대 동작 |
| --- | --- |
| 조회 중이거나 서버 요청이 실패함 | 로딩·실패·재시도를 구분하고 이전 결과를 새 문서 결과처럼 보여주지 않음 |
| 빈 결과 또는 찾지 못한 조건 | 미확인과 처리 실패를 구분하고 임의의 0·없음을 채우지 않음 |
| 원문에 없음이 명시됨 | 미확인과 구분하고 근거를 보여줌 |
| 숫자 0이 유효한 값으로 전달됨 | 빈 값으로 숨기지 않고 단위·의미와 함께 표시 |
| 선택한 조건의 위치가 잘못됨 | 엉뚱한 구간을 정상 근거처럼 강조하지 않음 |
| 이모지·줄바꿈·표 헤더가 포함됨 | 합의한 위치 기준에 따라 같은 원문 구간을 찾음 |
| 같은 금액의 서로 다른 한도가 있음 | 금액만으로 공유 한도로 합치지 않음 |
| 한도를 공유하거나 관계가 불명확함 | 명시된 공유 관계와 검토 필요 상태를 구분 |
| 저장이 실패하거나 중복 클릭함 | 초안을 유지하고 중복 제출·거짓 성공 표시를 막음 |
| 저장 후 새로고침함 | 서버에 저장한 값이 유지되고 최초 예측도 보존됨 |
| 미저장 변경이 있는데 문서를 바꾸거나 내보냄 | 변경 내용을 알리고 저장·취소를 선택할 수 있게 함 |
| CSV 내보내기가 실패함 | 실패를 안내하고 실제 파일 생성·저장 완료로 표시하지 않음 |

실제 자료에서 모든 예외를 자동으로 찾는 기능을 요구하는 것은 아닙니다. 이번 주에는 전달받은 상태와 확인한 오류를 화면이 정직하게 처리하는지 확인합니다. 필요한 검증 방식은 팀과 정하고, 불필요하게 큰 테스트 환경부터 만들지 않습니다.

## 8. 성능 비교를 위해 프런트엔드에서 지킬 점

교수님 피드백을 반영해 규칙 도구와 모델 도구의 차이가 화면 편의성 때문에 생기지 않도록 합니다.

- 규칙과 모델 결과는 같은 데이터 형식과 같은 검토 화면으로 보여줍니다.
- 수정·근거 확인·저장·CSV 기능을 한쪽에만 제공하지 않습니다.
- 두 결과를 다른 디자인으로 따로 만들거나, 한쪽만 상세 근거를 보여주지 않습니다.
- 최초 예측과 사람의 수정 결과를 구분해 보존하도록 백엔드 계약을 확인합니다.
- 업무 실험에는 같은 필수 항목과 완료 기준을 적용할 수 있도록 화면 흐름을 손영원과 확인합니다.

모델의 Strict Span Micro-F1은 손영원이 수정 전 예측으로 평가합니다. 박세렴은 화면에서 수정한 값을 모델 성능으로 보고하지 않도록 이력이 분리되는지 확인합니다. UI 응답시간이나 조회 대기시간도 모델의 CPU 블록 처리시간과 다른 측정입니다.

이번 주에는 화면 사용성과 기본 연동을 점검합니다. 수작업·규칙 도구·모델 도구의 정식 업무 비교 실험이나 현업 생산성 향상 수치를 만들지는 않습니다. 이후 손영원과 과제·순서·시간 측정 기준이 정해지면 필요한 기록 기능을 추가합니다.

| 공통 형식 버전과 남은 미정 항목 | 미기록 |
| 예외 상황 점검 성공·실패·미확인 수 | 미집계 |
| 다른 팀원의 실행·검토 결과 | 미확인 |
| 이번 주 사용한 시간·다음 주 확보 가능 시간 | 미기록 |

화면이 보이는 것과 실제로 저장되는 것, 합성 예시가 동작하는 것과 실제 문서가 처리되는 것을 각각 구분해 보고합니다.

## 12. 다음 주로 넘어가기 위한 기준

다음 항목이 준비됐는지 확인한 뒤 다음 주에 비교 화면과 검토 기능을 어디까지 확장할지 정합니다.

- [ ] 팀원이 실행할 수 있는 프런트엔드와 안내가 있습니다.
- [ ] 합의한 공통 형식으로 원문과 여섯 조건을 표시합니다.
- [ ] 선택 조건의 근거를 찾고, 위치가 불확실하면 그 사실을 안내합니다.
- [ ] 미확인·명시적 없음·검토 상태·저장 상태를 구분합니다.
- [ ] 실제 서버 저장 후 재조회에서도 수정 결과가 남습니다.
- [ ] 최초 예측을 수정 결과와 구분해 확인합니다.
- [ ] 서버 CSV와 예외 상황을 확인한 범위, 아직 막힌 범위를 기록했습니다.

저장·근거·형식 문제가 남아 있다면 다음 주 첫 작업으로 보완합니다. 독립적으로 진행할 수 있는 화면 작업은 계속하되, 임시 응답만으로 전체 연동이 끝났다고 판단하지 않습니다. 통과한 항목과 미달한 항목을 PM과 확인한 뒤 다음 주 계획을 작성합니다.

### 주간 점검 때 공유할 양식

```text
[박세렴 1주차 점검 / 2026-11-08]

1. 완료한 작업과 코드·화면·PR 경로:
2. 실제 실행 명령과 사용 버전:
3. 임시 응답으로만 확인한 기능:
4. 실제 API로 확인한 조회·저장·재조회·CSV 범위:
5. 사용 자료가 합성인지 실제인지와 확인한 원문 근거:
6. 공통 형식·문자 위치·검토 상태에서 남은 문제:
7. 예외 상황 점검 결과와 가장 큰 장애물:
8. 다른 팀원에게 필요한 정보와 다음 확인일:
9. 이번 주 사용한 시간과 다음 주 확보 가능 시간:
10. 다음 주로 넘어가기 위한 기준 중 미달한 항목:
```
